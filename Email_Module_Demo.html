What this module does

Coral Academy gets emails from parents every day — questions about classes, billing, admissions, and more. This module reads every email that comes in, figures out what it's about, writes a suggested reply using AI, and lets a staff member check it and send it (or fix it first).

Think of it like having an assistant who reads every email, sorts it into the right pile, drafts a reply for you, and hands it over to approve — so nobody ever starts from a blank page.

Features

Thirteen things you can show, grouped by where they sit in an email's journey — from arriving in the inbox to landing safely in the Sent folder.

Getting mail in

Inbox Dashboard

Every email in one view — sender, subject, category, priority, reply status. Search, filter, and page through results. The list quietly refreshes itself every few seconds, so new mail just appears.

Real-Time Reading

New emails are picked up the instant they arrive, via Gmail's own push notifications — with a backup check every 5 minutes in case one is ever missed.

Filtering Out Junk

System notifications, password resets, and newsletters are recognized automatically and kept out of the main inbox, so staff only see what actually needs attention.

Understanding & answering

Automatic Sorting

Every email is read by AI and sorted into Admissions, Billing, Teacher, or General — and flagged Urgent if needed. AI also decides whether it can safely draft a reply, or whether a human should handle it directly.

AI-Written Draft Replies

Grounded only in real Help Center articles, real class data, and (carefully) real past staff replies — never invented. If it genuinely doesn't know, it says so, and never promises a follow-up it can't guarantee.

Learning Coral's Writing Style

Every real reply staff sends feeds a style library future drafts learn from, so AI replies sound like Coral Academy actually wrote them. Personal details are stripped out before anything is stored.

Sending

Sending Replies

Staff reviews the draft, edits if needed, and hits Send. Threading is automatic, so replies join the right conversation instead of starting a new one.

Compose & Bulk Send

Write to one person, or up to 100 at once via typed list, CSV upload, or paste. Each name can personalize automatically. Bulk sends run in the background so the page never freezes.

Attachments

Incoming attachments can be viewed and downloaded. Outgoing attachments are supported on both replies and new Compose messages.

Sent-Mail Sync

Reply straight from Gmail instead of the app, and the system notices and pulls it in automatically within the hour — the conversation stays complete either way.

Housekeeping & trust

Trash & Restore

Emails can be moved to Trash and brought straight back if needed — nothing is ever permanently lost by accident.

AI Insights

A dedicated page shows how the AI is performing — replies generated, errors, tokens used, response time — and any single email's AI activity can be looked up directly.

Everyone's Own Time Zone

Every timestamp is shown in whoever's viewing it own local time — never a fixed, confusing company timezone.

Under the hood

Technical details

How the pieces above are actually built — organized by the part of the journey they handle.

The core pipeline process_email.py

The entry point for every incoming email. For each one:

  • Checks it isn't a duplicate — keyed on the email's own Message-ID header.
  • Finds the parent message for threading — first via In-Reply-To, then falling back to the References header, so replies from clients that only set References still join the right conversation instead of starting a disconnected new thread. If neither turns up a parent, the message's own Message-ID becomes the thread's anchor, so later replies still have something to attach to.
  • Runs classification and content-retrieval in parallel (ThreadPoolExecutor) — ai_classifier.py, vector_search.py, and knowledge_search.py all fire at once rather than one after another, so an email shows up fully processed faster.
  • Each parallel embedding lookup gets its own isolated client (new_embedding_client() / close_embedding_client()) — the shared default client isn't safe to call from two threads at the same time.
  • Reranks retrieved historical emails (rag_reranker.py) to drop anything that only matched loosely.
  • Hands everything to reply_generator.py, then saves the result via database.py.

Contact Form enquiries branch off this same pipeline but are their own module from there — see the dedicated Contact Form document.

Classification ai_classifier.py

ai_triage() sends the subject and body to gpt-5-nano and gets back category, priority, a one-line summary, a confidence score, and whether AI can safely draft a reply.

  • A few rules sit in Python on top of the model's own judgment: Teacher Portal notifications are always forced to category Teacher; keywords like "complaint," "refund," or "legal" always force human review, no matter what the model decided.
  • Now fully logged to ai_logs under category Classification — previously only reply-drafting was logged, so a wrong classification left no trail at all.

Reply generation reply_generator.py prompt_builder.py

The full rulebook the AI follows when writing a reply — the most heavily refined part of this project.

  • Source priority: Current Email > Knowledge Base > Historical Emails, and historical emails only count if 2–3 clearly agree with each other and don't contradict the Knowledge Base.
  • Question-type routing: Pricing, Refund, Policy, and Schedule questions must come from the Knowledge Base only — never historical emails, no matter how consistent they look.
  • Audience checks: some Knowledge Base articles and historical emails are written for teachers, not parents — checked before use, so internal staff process details don't leak into a parent's reply.
  • Plan-specific accuracy: Pay Per Class and Coral Unlimited have different rules (only Coral Unlimited has a pause feature) — one plan's mechanics never get blended into an answer about the other.
  • Date-aware reasoning: the email's actual received date is passed in, so timing questions (like refund eligibility) are reasoned about correctly instead of guessed.
  • Tone: apologizes only when something genuinely went wrong, always closes with thanks, stays direct without being blunt.
  • Signature & greeting: matched to the actual sending account, using the customer's name when it's on file.
  • Prompt-injection guard: the customer's email is always treated as data to respond to, never as instructions to follow.

Every call is logged via ai_logger.py — model, tokens, response time, which sources were used, and the full error on failure. A logging failure can never crash a reply that was already successfully generated.

Filtering automated mail email_filter.py

is_automated_email() runs before AI ever sees a message: headers first (Auto-Submitted, List-Unsubscribe), then known automated senders, then database-driven rules from email_filter_rules — editable without touching code.

  • Bug found and fixed this project: overly broad subject rules ("payment," "subscription," "renewed") were catching genuine customer emails that simply used those common words. Replaced with exact-phrase rules ("subscription renewed successfully," "subscription cancelled:") that only match real automated system messages.

Real-time ingestion gmail_watch.py gmail_history.py email_reader.py

  • gmail_watch.py registers and renews Gmail's push-notification subscription, re-registered daily as Google requires.
  • gmail_history.py fetches exactly what changed since the last known point (historyId) instead of rescanning the whole mailbox.
  • email_reader.py is the 5-minute polling backup, with a lock so overlapping runs queue instead of colliding.

Sent-mail sync sync_sent_gmail.py

Runs hourly to pull in replies sent directly from Gmail. The most heavily reworked piece of this project — replaced a hardcoded date and a "last 50" slice with a real checkpoint tracked in sync_log.

  • If a backlog exceeds the 500-message safety cap, the checkpoint advances only to the oldest processed message — never to "now" — so nothing older is silently skipped.
  • If some messages fail but others succeed, the checkpoint advances to the newest successfully-handled message, so one bad message can't block every future run forever.
  • Failed messages get one bounded automatic retry (sync_failed_messages), relocated by Message-ID since IMAP sequence numbers aren't stable over time — a second failure leaves it for manual review, via a small panel right on the main dashboard with one-click Retry/Delete per message.
  • ⚠️ Known issue: on the rare truncated-run path (backlog > 500), the code currently grabs the newest 500 messages instead of the oldest 500 — confirmed live against a real mailbox that IMAP results come back oldest-first, so "last 500" is the wrong end. Flagged, not yet fixed.

Knowledge & style pipeline vector_search.py learn_email_style.py embed_classes.py

  • vector_search.py / knowledge_search.py find similar past emails and relevant Help Center content by meaning, not just keyword match.
  • learn_email_style.py builds the historical-style library, automatically redacting emails and phone numbers before anything is stored (historical_email_redaction.py).
  • sync_classes.py / embed_classes.py keep Class Knowledge in sync with the real, live class catalog pulled directly from api.coralacademy.com.
  • embed_knowledge_base.py / refresh_knowledge_base.py keep Help Center content in sync and embedded for search.

Scheduling & reliability scheduler.py main.py

  • Every background job runs on a staggered schedule so heavy jobs never collide (a past cause of an out-of-memory crash).
  • Every scheduled job now durably logs success/failure to sync_log via a shared _run_logged_job() helper — previously only sent-mail sync did this; everything else only ever printed to a log that Render eventually rotated away.
  • main.py logs any unhandled error from a live request globally, and background tasks (bulk sends, the push-notification handler, saving a reply into the style library) are wrapped the same way — since FastAPI runs background tasks after the response is sent, a request-level error handler alone can never see their failures.

How errors are handled — four different safety nets

There isn't one single error-logging system — each kind of code fails differently, so each gets its own net:

  • An AI call (classification/drafting) → its own try/except → logged to ai_logs → visible on the AI Insights page.
  • A scheduled job (runs on a timer) → _run_logged_job() → logged to sync_log → no dashboard yet, direct query only.
  • A live web request → the global exception handler → a local log file (logs/app.log) + stdout — not the database, and typically wiped on every deploy/restart.
  • A background task (continues after the page already responded) → individually wrapped in _run_logged_job() → also logged to sync_log.

The global handler is scoped to live requests only — by the time a background task runs, the response is already sent and that handler is no longer in the call stack, so it structurally can't see background-task errors. That's why background tasks need their own wrapping rather than being automatically covered. As of this session every background_tasks.add_task(...) call is accounted for: three explicitly wrapped, one (sync_sent_gmail.main) already self-logging.

How the app stays fast — background work & concurrency

  • Running independent things at once (ThreadPoolExecutor) — classification, similar-email search, and Knowledge Base search don't depend on each other, so they fire simultaneously instead of one after another — the biggest speed win in the pipeline.
  • Background tasks (FastAPI BackgroundTasks) — sent-mail re-sync, saving a reply into the style library, and reacting to a push notification all happen after the page has already responded, so nobody waits on them.
  • Scheduled background jobs (APScheduler) — work with no human trigger at all, just its own timer, staggered so heavy jobs don't collide.
  • One isolated resource per thread, never shared — when several threads each need to talk to an external service, each gets its own client instance rather than sharing one. This exact bug class caused two real incidents fixed this session: a Supabase client race, and an OpenAI-library import deadlock on the first request after a restart.
