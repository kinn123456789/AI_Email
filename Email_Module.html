What this module does

Coral Academy gets emails from parents every day — questions about classes, billing, admissions, and more. This module reads every email that comes in, figures out what it's about, writes a suggested reply using AI, and lets a staff member check it and send it (or fix it first).

Think of it like having an assistant who reads every email, sorts it into the right pile, drafts a reply for you, and hands it over to approve.

Features

Thirteen things grouped by where they sit in an email's journey — from arriving in the inbox to landing safely in the Sent folder.

Getting mail in

Inbox Dashboard

Every email in one view — sender, subject, category, priority, reply status. Search, filter, and page through results. The list quietly refreshes itself every few seconds, so new mail just appears. Emails are always sorted the same way: unread before read, then by status (Needs Review first), then by priority (Urgent first), then newest first.

Real-Time Reading

New emails are picked up the instant they arrive, via Gmail's own push notifications — with a backup check every 5 minutes in case one is ever missed.

Filtering Out Junk

System notifications, password resets, and newsletters are recognized automatically and kept out of the main inbox, so staff only see what actually needs attention.

Understanding & answering

Automatic Sorting

Every email is read by AI and sorted into Admissions, Billing, Teacher, or General — and flagged Urgent if needed.

AI-Written Draft Replies

Grounded only in real Help Center articles, real class data, and (carefully) real past staff replies — never invented. If it genuinely doesn't know, it says so.

Learning Coral's Writing Style

Writing style comes from two places: a fixed set of tone rules built into the AI's own prompt (write naturally, keep it simple, keep paragraphs short), and real historical emails staff have sent, used as live examples for tone and phrasing. Personal details are stripped out of those historical emails before anything is stored.

Sending

Sending Replies

Staff reviews the draft, edits if needed, and hits Send. Threading is implemented, so replies join the right conversation instead of starting a new one.

Compose & Bulk Send

Write to one person, or up to 100 at once via typed list, CSV upload, or paste. Each name can personalize automatically. Bulk sends run in the background so the page never freezes.

Attachments

Incoming attachments can be viewed and downloaded. Outgoing attachments are supported on both replies and new Compose messages.

Sent-Mail Sync

Reply straight from Gmail instead of the app, and the system notices and pulls it in automatically within the hour — the conversation stays complete either way.

Supporting Features

Trash & Restore

Emails can be moved to Trash and brought straight back if needed — nothing is ever permanently lost by accident.

AI Insights

A dedicated page shows how the AI is performing — replies generated, tokens used, response time.

Everyone's Own Time Zone

Every timestamp is shown in whoever's viewing it own local time — never a fixed, confusing company timezone.

Under the hood

Technical details

How the pieces above are actually built — organized by the part of the journey they handle.

The core pipeline process_email.py

The entry point for every incoming email. For each one:

  • Checks it isn't a duplicate — keyed on the email's own Message-ID header.
  • The system tries to find which email this one is replying to, so it can keep the whole conversation together. It first checks the In-Reply-To header. If that is missing, it checks the References header instead. This way, even emails from apps that only use References still get placed in the correct conversation, instead of showing up as a new, separate thread. If neither header gives an answer, the email's own ID is used as the starting point of a new thread, so any future replies still have something to connect to.
  • Runs classification and content-retrieval in parallel (ThreadPoolExecutor) — ai_classifier.py, vector_search.py, and knowledge_search.py all fire at once rather than one after another, so an email shows up fully processed faster.
  • Each parallel embedding lookup gets its own isolated client (new_embedding_client() / close_embedding_client()) — the shared default client isn't safe to call from two threads at the same time. This covers both the 2 parallel lookups within one email and two different emails being processed at the same time, since each call creates and closes its own fresh clients either way.
  • Reranks retrieved historical emails (rag_reranker.py) to drop anything that only matched loosely.
  • Hands everything to reply_generator.py, then saves the result via database.py.

Contact Form enquiries branch off this same pipeline but are their own module from there — see the dedicated Contact Form document.

Classification ai_classifier.py

ai_triage() sends the subject and body to gpt-5-nano and gets back category, priority, a one-line summary, a confidence score, and whether AI can safely draft a reply.

  • Now fully logged to ai_logs under category Classification — previously only reply-drafting was logged, so a wrong classification left no trail at all.

Reply generation reply_generator.py prompt_builder.py

The full rulebook the AI follows when writing a reply.

  • Which source wins: the AI trusts the current email first. Next, it trusts the Knowledge Base. Old (historical) emails come last, and only count as backup if several of them (2 to 3) say the same thing and none of them disagree with the Knowledge Base.
  • How the AI decides what to check first: first, the AI asks: is this question about this customer's own account — their child's classes, their bill, their subscription? If yes, it will not guess. It either asks the customer for the missing detail, or just says it does not know. If the question is a general one instead — like pricing, refunds, or how something works — the AI checks the Knowledge Base first. Only when the Knowledge Base has no answer does it look at old emails for help. And even then, it needs proof, not just one example: it pulls 3 to 5 similar old emails, and at least 2 or 3 of them have to say the same thing. If they don't agree with each other, or if they go against what the Knowledge Base says, or if the email wasn't even written to a parent in the first place, the AI throws it out and does not use it.
  • Audience checks: some Knowledge Base articles and old emails were actually written to guide teachers, not to answer a parent's question. The AI checks who each one was really written for before using it. If it was meant for a teacher, it gets skipped — even if the topic matches — so a parent never ends up reading internal staff instructions by mistake.
  • Date-aware reasoning: the email's actual received date is passed in, so timing questions (like refund eligibility) are reasoned about correctly instead of guessed. Written in prompt_builder.py's "DATE REASONING" section, fed by the real email_date, never the current server time.
  • Tone: apologizes only when something genuinely went wrong, always closes with thanks, stays direct without being blunt.
  • Signature & greeting: matched to the actual sending account, using the customer's name when it's on file.
  • Prompt-injection guard: the customer's email is always treated as data to respond to, never as instructions to follow.

Every call is logged via ai_logger.py — model, tokens, response time, which sources were used, and the full error on failure. A logging failure can never crash a reply that was already successfully generated.

Filtering automated mail email_filter.py

Before the AI looks at any message, the system checks if it is an automated email, not a real message from a person. It checks three things, in order. First, it looks at the email headers, like Auto-Submitted and List-Unsubscribe. Next, it checks if the sender is a known automated sender. Last, it checks a list of rules stored in a database table called email_filter_rules.

Real-time ingestion gmail_watch.py gmail_history.py email_reader.py

  • gmail_watch.py registers and renews Gmail's push-notification subscription, re-registered daily as Google requires.
  • gmail_history.py fetches exactly what changed since the last known point (historyId) instead of rescanning the whole mailbox.
  • email_reader.py is the 5-minute polling backup, with a lock so overlapping runs queue instead of colliding.

Sent-mail sync sync_sent_gmail.py

Runs hourly to pull in replies sent directly from Gmail.sync_log.

Knowledge & style pipeline vector_search.py learn_email_style.py embed_classes.py

  • vector_search.py / knowledge_search.py find similar past emails and relevant Help Center content by meaning, not just keyword match.
  • Both old emails and Knowledge Base/Help Center results get a second check by AI (rag_reranker.py). This happens before they are used to write the reply. For old emails, the AI looks at the top 30 matches. It keeps only the 2 or 3 that are truly useful. It throws away the ones that only look similar on the surface. The Knowledge Base (knowledge_search.py) now gets the same kind of check. The AI collects several possible matches. It keeps only the ones that actually answer the question. It does not keep ones that are just about a similar topic. This matters because a Knowledge Base article can sound related to a question without really answering it. Plain similarity matching cannot tell the difference between the two. In both cases, the AI chooses the good matches itself. It does not simply trust whichever match scored "closest" on paper.
  • learn_email_style.py builds the historical-style library, automatically redacting emails and phone numbers before anything is stored (historical_email_redaction.py). This is additive: prompt_builder.py's fixed "WRITING STYLE" baseline (short paragraphs, no corporate language, always close with thanks) applies to every reply regardless of historical examples — the 2-3 selected historical examples layer on top of that baseline, they don't replace it.

    Why do we need both? They do two different jobs. The baseline gives simple rules, like "keep it short"." These rules do not give the AI anything real to copy. Old emails are different. The AI reads real emails that staff sent before — the exact words, the exact subject, the exact body. This shows the AI how Coral Academy really talks: the words staff use, how they start and end an email, and small phrases only this team uses. A rule like "do not sound robotic" cannot teach that. The baseline is always there, even if there are no old emails to use. Old emails are what make the reply sound like it came from this exact team, not just any company.
  • sync_classes.py / embed_classes.py keep Class Knowledge in sync with the real, live class catalog pulled directly from api.coralacademy.com.
  • embed_knowledge_base.py / refresh_knowledge_base.py keep Help Center content in sync and embedded for search.

Scheduling & reliability scheduler.py main.py

  • Every background job runs on a staggered schedule so heavy jobs never collide.
  • Every scheduled job now durably logs success/failure to sync_log via a shared _run_logged_job() helper .
  • main.py logs any unhandled error from a live request globally, and background tasks (bulk sends, the push-notification handler, saving a reply into the style library) are wrapped the same way — since FastAPI runs background tasks after the response is sent, a request-level error handler alone can never see their failures.

How errors are handled — four different safety nets

There isn't one single error-logging system — each kind of code fails differently, so each gets its own net:

  • An AI call (classification/drafting) → its own try/except → logged to ai_logs → visible on the AI Insights page.
  • A scheduled job (runs on a timer) → _run_logged_job() → logged to sync_log → no dashboard yet, direct query only.
  • A live web request → the global exception handler → a local log file (logs/app.log) + stdout — not the database, and typically wiped on every deploy/restart.
  • A background task (continues after the page already responded) → individually wrapped in _run_logged_job() → also logged to sync_log.

The global handler is scoped to live requests only — by the time a background task runs, the response is already sent and that handler is no longer in the call stack, so it structurally can't see background-task errors. That's why background tasks need their own wrapping rather than being automatically covered. As of this session every background_tasks.add_task(...) call is accounted for: three explicitly wrapped, one (sync_sent_gmail.main) already self-logging.

How the app stays fast — background work & concurrency

  • Running independent things at once (ThreadPoolExecutor) — classification, similar-email search, and Knowledge Base search don't depend on each other, so they fire simultaneously instead of one after another — the biggest speed win in the pipeline.
  • Background tasks (FastAPI BackgroundTasks) — sent-mail re-sync, saving a reply into the style library, and reacting to a push notification all happen after the page has already responded, so nobody waits on them.
  • Scheduled background jobs (APScheduler) — work with no human trigger at all, just its own timer, staggered so heavy jobs don't collide.
  • One isolated resource per thread, never shared — when several threads each need to talk to an external service, each gets its own client instance rather than sharing one.

Manageable email accounts database.py main.py templates/settings.html

Adding or removing a monitored mailbox no longer requires editing code or redeploying. Three mailboxes (support@, lucy@, engineering@coralacademy.com) are "core" — always present, tied to fixed environment variables, and not deletable from this page. Anything beyond those three is managed from a real page: Settings → Email Accounts.

[ + Add Email ]

Clicking "Add" first checks the address is real and actually reachable, by calling the Gmail API for it (get_gmail_service(email).users().getProfile()) before saving anything — a typo'd or non-Workspace address fails this check and is never stored, instead of silently failing every poll afterward. Once saved, it lands in the email_accounts table, and the app starts polling/watching it on the very next scheduler cycle — no restart needed. Deleting an account marks it inactive and stops polling; the three core mailboxes can't be deleted here.

Every reader of the account list (email_reader.py, sync_sent_gmail.py, learn_email_style.py, gmail_watch.py, gmail_history.py) calls get_all_email_accounts() fresh each time rather than caching it, so a newly added mailbox is picked up immediately by all of them. The dashboard's mailbox filter and source badges are also generated dynamically from this same list, instead of being hardcoded to the three core mailboxes.

Note: Adding a new mailbox in Settings only makes the system start reading and watching it — it does not give the AI any new knowledge. If the new mailbox gets questions about topics the Knowledge Base and historical emails don't cover yet, the AI will not know the right answer, because it has nothing to learn from. The Knowledge Base and historical emails need to be updated separately whenever a newly added mailbox handles genuinely different kinds of enquiries.
